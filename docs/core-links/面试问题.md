# 后端面试高分话术整理

> 涵盖 Feed 流架构设计、设计模式实战抉择、RabbitMQ 可靠消费三大核心模块

------

## 一、Feed 流架构设计

### 核心痛点

Feed 流的本质挑战是「写扩散（Push）」模型遇上大 V 用户时的性能灾难。逐条写入 Redis 的方案会引发三类问题：

1. **网络 I/O 爆炸**：百万粉丝需发起百万次 Redis 网络请求，RTT 延迟成倍放大。
2. **消费者阻塞**：MQ 消费线程被超长 for 循环拖死，可能卡顿数十秒乃至上百秒。
3. **内存灾难**：千万粉丝的写扩散会撑爆 Redis 内存，纯 Push 模式无法持续。

------

### 递进式优化方案（三层防守）

#### 第 1 层：MQ 异步化解耦（当前方案）

采用写扩散（Push）+ MQ 异步化架构。发布动态时，主业务线程瞬间返回，将耗时的 Redis 写入操作抛给 MQ 后端消费者异步处理，保证前端发布体验的极速响应。

- **适用阶段**：用户规模尚未庞大的早期阶段。
- **核心优势**：读取 Feed 流时直接读自己的 ZSet，延迟最低。

#### 第 2 层：Redis Pipeline 批量写入（万粉级优化）

for 循环逐条写入会造成大量网络 RTT 放大效应。解决方案：在 `RedisUtil` 中封装基于 Spring `SessionCallback` 的 Pipeline 批量执行。

- 将数万粉丝的 ZSet Key 在内存中快速组装，**每批 500 ～ 1000 个**，打包成一条 Pipeline 指令一次性发送。
- 耗时从原本的 `N × 网络延迟`，骤降为接近 `1 × 网络延迟`。
- **实测效果**：万粉级写扩散耗时从数十秒/超时，优化至**几百毫秒级别**。

#### 第 3 层：推拉结合模型（千万粉级终极方案）

对于超级大 V（千万粉丝量级），纯 Push 写扩散已无法支撑，架构演进为**推拉结合（Push & Pull）**模式：

| 用户类型    | 处理策略                      | 原理                                  |
| ----------- | ----------------------------- | ------------------------------------- |
| 活跃粉丝    | 定向 Push 短索引              | 只推送一小部分高活跃用户，降低写压力  |
| 潜水/僵尸粉 | 上线时触发 Pull 拉取          | 主动查大 V 发件箱，合并排序后返回前端 |
| 大 V 本人   | 写入固定发件箱（Outbox ZSet） | 不再做循环写扩散，彻底消除内存炸弹    |

> **核心价值**：「推大盘活跃，拉沉寂用户」，在性能、内存和实时性之间取得最优平衡。

## 二、设计模式实战：策略模式与模板模式的抉择

> **核心原则**：策略管分发，模板管骨架。没有重复骨架，就拒绝过度模板化。

### 为什么全盘使用策略模式（Strategy）？

互动模块面对博客、商品、店铺等多种业务载体，若将所有逻辑揉入单一 Service 并用 if-else 判断枚举，代码极度臃肿，严重违背**开闭原则（OCP）**。

**解决方案**：定义 `LikeStrategy`、`StarStrategy` 等接口，配合简单工厂路由。后续新增「短视频点赞」只需注入一个新实现类，核心逻辑零改动，解耦彻底。

### 为什么在 ES 同步 / 热榜计算 引入模板方法模式（Template Method）？

在 `syncUserResource`（ES 数据同步）和 `AbstractHotRankStrategy`（热榜计算）中，各实现类存在大量高度一致的流程代码：组装 `UserResourceMessage`、拼接文档 ID、注入常量名、通过 `RabbitTemplate` 发送 MQ。这是典型的**样板代码（Boilerplate Code）**，一处改处处改，极易出错。

**解决方案**：引入模板方法模式，分工明确：

- **父类（模板）**：将完整的发 MQ 流程骨架封死在 Abstract 基类中。
- **子类（策略）**：仅实现 `getSourceData()`、`getBizDomain()` 等钩子（Hook）方法，只提供差异化的元数据，不再直接依赖 MQ 组件，职责单一到极致。
- **收益**：完美体现 DRY 原则（Don't Repeat Yourself），一处修改，全局生效。

### 克制力：为什么不对所有方法套模板？

以 `transLikeCountFromRedis2DB` 为例，其核心逻辑仅是一次 RPC/Feign 调用：

```java
remoteBlogService.updateLikeCountBatch()
```

这是「**异构端点透传**」，没有多步骤同构业务流，强行套模板只会增加无意义的嵌套层级，破坏代码直观性，违背 KISS 原则。

| 维度           | 使用模板模式 ✅              | 不使用模板模式 ❌             |
| -------------- | --------------------------- | ---------------------------- |
| 代码特征       | 多步骤同构业务流            | 单步异构端点透传             |
| 代表方法       | `syncUserResource`（发 ES） | `transLikeCountFromRedis2DB` |
| 痛点           | 样板代码大量重复，一改多错  | 无重复逻辑，无痛点           |
| 引入模板的收益 | DRY，骨架复用，职责单一     | 无收益，只增加嵌套复杂度     |

> **真正的架构不是为了用设计模式而用，而是为了解决痛点才用，没有痛点绝不生搬硬套。**

## 三、RabbitMQ 可靠消费：幂等防重与死信重试

### 核心痛点

在微服务架构下，如果只是写一个简单的监听方法（加个 try-catch），会遇到三类致命问题：

1. **重复消费（非幂等灾难）**：网络抖动、ACK 丢包、Broker 重发补偿机制，都会导致同一条消息被多次消费。对扣除余额、增加积分、创建订单等操作，后果是严重资损和脏数据。
2. **死循环阻塞（毒消息堆积）**：下游系统宕机或代码空指报错后，若简单地 `basicNack(requeue=true)` 重新投递，消息会以光速疯狂重回队列再次报错，形成永远消费不掉的**「毒消息（Poison Pill）」**，迅速吃满消费线程池，CPU 瞬间飙升到 100%。
3. **消息永久丢失（掩耳盗铃）**：异常时顺手 `basicAck` 或 `basicNack(requeue=false)` 丢弃，因「数据库偶尔闪断」失败的宝贵消息就此永久消失。

------

### 递进式解决方案（三层防守）

#### 第 1 层：Redis SETNX 幂等防重（保障幂等性）

防重复消费不能依赖 MQ 提供的 Only-Once 承诺，必须自建双重保障：

**发送端**：通过统一的 `MqMessageSendUtils` 收口拦截，为每一条消息的 Header 中强制注入全局唯一的 `MessageId`（UUID），作为防重的核心基石。

**消费端**：坚守第一道防线——

- 将模块前缀与 `MessageId` 拼接成 Key，调用 Redis `setIfAbsent`（SETNX 指令）尝试获取一把有效期为 **24 小时**的互斥锁。
- **抢到锁**：首次消费，放行执行核心业务逻辑。
- **未抢到锁**：大概率是重试投递，打 INFO 日志「重复消息已跳过」，立即 `basicAck` 让多余的消息体面安息。
- **无 MessageId**：直接 `basicAck` 签收拒退（防御脏数据入侵）。

#### 第 2 层：删锁 + 抛错的闭合设计（解决首次执行中途崩溃问题）

**问题**：第一次拿到锁但业务执行到一半系统崩溃，MQ 重发时会被 Redis 锁挡住当成重复消息丢弃。

**解决方案**：两件套「主动拔锁设计」——

1. 核心业务逻辑爆出任何异常，在 catch 的**第一现场**立即调用 `redisService.deleteObject(key)`，删除防重锁，为后续重发「让路」。
2. 紧跟着向外抛出 `RuntimeException`，明确告知框架：我出错了，请用重试机制来捞我。

> **「删锁抛错」两件套，完美保障了后续重发的同 ID 消息能顺利叩门重抢锁。**

#### 第 3 层：Spring Retry + 死信队列 DLQ（终极兜底，防雪崩）

纯粹 `basicNack(requeue=true)` 会引发毒消息死循环，因此在外围架构搭建弹性拦截与兜底机制：

```
消费失败
  └─ Spring Retry 本地截停（不向 Broker 发任何信号）
       ├─ 间隔 1 秒重试，共 3 次
       │    └─ 屏蔽瞬时网络抖动，零网络开销，零 Broker 压力
       └─ 3 次全部失败
            └─ Spring 发出 requeue=false 的 Reject 信号
                 └─ Broker 将消息流转进绑定的死信队列（x-dead-letter-exchange）
                      ├─ 主队列瞬间恢复清净，正常消息零堆积
                      └─ 死信队列触发红色报警，运维一键溯源
```

**为什么用 Spring 本地 Retry 而非 MQ 侧重试？**

Spring 本地重试完全在线程内完成，不占用网络开销，不对 MQ Broker 产生任何交互压力，能有效屏蔽瞬时网络抖动。

------

### 完整防护体系总结

| 层级     | 机制                                       | 解决的问题                   |
| -------- | ------------------------------------------ | ---------------------------- |
| 链路注入 | `MqMessageSendUtils` 强制注入 `MessageId`  | 防重基石缺失                 |
| 缓存幂等 | Redis SETNX 行级锁 + 无 ID 即拒退          | 重复消费导致资损             |
| 闭合退路 | 异常时先删锁后抛错                         | 首次执行中途崩溃导致消息丢失 |
| 短效补偿 | Spring Retry 本地重试（1 秒间隔，共 3 次） | 瞬时抖动导致的偶发失败       |
| 降级兜底 | 死信队列 DLQ + 报警探针                    | 毒消息死循环压垮机器         |

> 这套涵盖链路注入、缓存幂等、短效补偿与降级兜底的全维度组合拳，将 MQ 消费雷区升级为高可用防护体系。

## 四、RabbitMQ 消息堆积：事前预防与事后救火

### 核心定调

消息堆积（Message Accumulation）是 MQ 架构的最后一块硬骨头。正确的定调方式：

> 只要上下游处理能力存在天然的剪刀差，堆积就无法 100% 避免。但在当前架构中，因错误代码或毒消息（Poison Pill）导致的**死循环堆积已被彻底消灭**。目前唯一可能引发堆积的，只剩下纯物理层面的「生产速度远大于消费速度」（如大促秒杀瞬间）。针对这种场景，有一套完整的事前预防与事后救火架构。

------

### 递进式解决方案（三层防守）

#### 第 1 层：事前预防——毒消息隔离（Spring Retry + 死信 DLQ）

**问题根源**：消费出现异常时若直接 `Nack(requeue=true)`，消息会瞬间重回队列头部立马再次报错，一秒钟能死循环成千上万次，直接打满 MQ 集群网络和消费线程池，酿成史诗级堆积。

**解决方案**：Spring Local Retry + 死信「断尾求生」机制——

```
消费异常
  └─ Spring Retry 本地重试（1 秒间隔，共 3 次，不走网络，零 Broker 压力）
       └─ 3 次全部失败
            └─ Reject(requeue=false) 强制引流至死信队列
                 └─ 主干道永不因脏数据堵车，死信队列触发报警
```

> **关键点**：本地重试完全在内存中完成，不增加 Broker 哪怕一丁点压力。

#### 第 2 层：性能调优——合法流量洪峰的并发放大

面对双十一级别的瞬时流量洪峰，从三个层面横向扩展消费能力：

**① 惰性队列保护 Broker 内存**

在声明秒杀订单队列时加入 `@Argument(name = "x-queue-mode", value = "lazy")`，RabbitMQ 直接将消息落盘而非塞入内存，完美防止 Broker 内存被撑爆导致宕机。

**② 提升单机并发线程数**

通过调整 `bootstrap.yml` 中的 `concurrency` 和 `max-concurrency`，将单机监听线程数从默认单线程扩至 20 线程，直接放大单机消费吞吐。

**③ 优化单次消费耗时**

堆积的源头永远是消费逻辑太慢。排查方向：

- 有没有未走索引的慢 SQL？
- 有没有可以 Pipeline 批量写入的 Redis 操作？

单次消费从 500ms 压缩到 50ms，总体堆积消化速度提升十倍。

#### 第 3 层：事后救火——千万级史诗堆积的「紧急分流扩容法」

当已有千万量级堆积，且数据库/下游服务已因雪崩超时不堪重负时，常规加机器是杯水车薪。采用**「紧急分流（Shunting）扩容法」**：

```
Step 1  临时阻断重逻辑
        停掉原来「慢消费者」（查库 + 调外系统），
        换上「哑巴消费者（Dummy Consumer）」

Step 2  高速转运 + 多倍分流
        哑巴消费者以光速将 1000 万条消息抽出，
        按哈希规则均匀分发到新建的 10 ～ 20 个临时子队列

Step 3  饱和式救援
        申请 20 台云服务器，以 10 倍兵力部署真实消费者，
        分别消费各自的临时子队列
```

**效果**：原本需要消化一整天的历史堆积，不到一小时即可清空。

> 这是架构设计中「空间换时间」与「快读细消」分治思想的最佳体现。

------

### 消息堆积处理完整总结

| 层级     | 手段                                     | 解决的问题                   |
| -------- | ---------------------------------------- | ---------------------------- |
| 事前预防 | Spring Retry + 死信 DLQ 断尾求生         | 毒消息死循环导致的恶性堆积   |
| 性能调优 | 惰性队列 + 并发线程数 + 慢逻辑优化       | 合法流量洪峰下的消费能力不足 |
| 事后救火 | 哑巴消费者分流 + 临时子队列 + 云资源扩容 | 千万级史诗堆积的极限清空     |

> 高段位的回答不是「加机器」，而是先隔离恶性堆积，再调优消费吞吐，最后备好极限救火预案。
