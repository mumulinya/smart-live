## 2. 每一步的技术细节与面试追问

### Step 1~3：打通知觉系统的基石 —— 长效记忆回填

**做了什么：**

在 `UserAiMessageServiceImpl` 处理每一轮发来的提问时，立刻将身份和 `chatId` 一分为二入库持久留样。然后去取回这桌会话先前的 `[Conversation history]` 上下文数组，强制打包作为 `FrameworkRoutingStrategy` 给到大模型的 `userMessage` 头顶。这是让它能听懂“那上一家店呢”这类指代词的核心。

**面试追问与回答：**

| 问题                                                           | 回答                                                                                              |
| :------------------------------------------------------------- | :------------------------------------------------------------------------------------------------ |
| 记忆越吃越多导致超过了 GPT 的 Context-Window 最大 Token 上限报错怎么办？ | 在设计 `MessageTableChatMemoryManager` 载入内存池时，我们采用了严格的切边策略，只捞取最近的 N 条核心高浓对话；对于更古老的会话，若要维持记忆，会在后台开启协程使用 Text-Summarization 方式把冗长的一千句对白浓缩成 100 字的人设梗概带入 prompt，实现变相永流传。 |

---

### Step 4~5：消解人工 if-else 的大脑 —— Agent 框架级路由

**做了什么：**

我们不去硬编码判断“如果用户打出‘店铺’字样进店函数”。通过引入阿里原生 `LlmRoutingAgent`，建立司令部总闸。把专门处理商品的、店铺的四个子 `Agent` 挂载在名下，只给司令部一句话 Instruction 提示：“根据语气和目标决定发配给下属”，接下来所有分析和分桶均由大模型自己消化决定。

**面试追问与回答：**

| 问题                                                           | 回答                                                                                              |
| :------------------------------------------------------------- | :------------------------------------------------------------------------------------------------ |
| 把路由分发权全交给 AI Agent 司令部有什么不可隐患？如何兜底？   | AI 随时可能发神经将问题胡乱选定，且可能输出带有废话 JSON 的深层结构树。为此，我在业务代码重写了极为变态的 `extractFinalJsonFromState` 字典树深探。不论这个模型把子任务发配得多么乱，最后我会利用树形深度遍历拦截提取最末端的合法回答。只要失败降级，最后无条件被转走交给 `generalAgent` 闲聊机应对。|

---

### Step 6~8：打破幻觉，接驳企业知识库 —— Milvus RAG 并网打捞

**做了什么：**

普通大模型回答“杭州哪家烤肉好吃？”是纯凭网上的幻觉背书。
我们赋予了它 RAG 挂件。当 `shopAgent` 被激活后，会在背后隐形调用我们自建的 Milvus 向量引擎库。由于在入库阶段我们把店铺带有经纬度信息一并植入。这一步查询，我们能够下达带有严格的 `Filter Expression （如限制半径 5km）` 并附带 Embedding 矩阵的双压查询，它会捞出库里最火热的“大牛烤肉店”喂给 GPT 完成二次提纯总结！

**面试追问与回答：**

| 问题                                           | 回答                                                                                              |
| :--------------------------------------------- | :------------------------------------------------------------------------------------------------ |
| Milvus 的向量搜索，和上一篇你写的 Elasticsearch 多字段查询有什么截然不同？| ES 是字符词切片游戏（TF/IDF倒排），搜“烤肉”搜不出“炙牛肉”，词根一旦切错完全没用；而向量 RAG 机制是把大段语义高潮变成一串由几千个小数构成的多维雷达图。当顾客问：“这两天郁闷想多吃点肉”，这句提示根本没包含任何实体店铺词，但因为向量角正弦距离计算相近，依然可以把能疗愈的肉类餐厅全盘端出，实现了降维的人类意图匹配！|

---

### Step 9~11：多模态响应截断与 SSE (Server-Sent Events) 打字机

**做了什么：**

大模型处理不仅慢有时还要回拉卡片地址，等到拿完整串全文本让前端一下弹出来客户早就急关掉 App 了。
利用 Spring WebFlux + Reactor 发射器：
- `chat()` 接口硬性返回 `Flux<ServerSentEvent<String>>`；
- 所有接管到的模型回答内容立即碎片化顺带建立单向长通管道 `builder().event("message").data(chunk)`。
- 通过特殊的 `RecommendationCardHelper` 收口，如果检测到底部大模型携带下传了标准的规范商品结构化 Json 对象，代码立刻截掉这部分隐藏文本，独立重构为 `event: card_render` 发给前端直接爆出一个可购物下单的原生安卓卡片！

**面试追问与回答：**

| 问题                                           | 回答                                                                                              |
| :--------------------------------------------- | :------------------------------------------------------------------------------------------------ |
| 为什么选了 SSE 单工通信来传输模型文字，而不是像之前的聊天一样用 WebSocket 全双工通信？| WebSocket 是重型运载舰，维持通道高开销且前后端要全改双向状态机协议；但大模型的业务场景是：用户发一下接口，模型在后续几十秒拼命流式吐回答。方向是绝对的单向水压。“发送一条短请求 -> 获取一段长流式纯文本下发”，没有哪项技术比天生建立在 HTTP 上、更轻捷、全浏览器无忧支持的 SSE 更优美匹配了。|

## 4. 面试 10 分钟讲述模板

> **讲述思路：第一步聊明白聊天记忆的回血与流式网络交互；第二步深聊中台 Agent 的路由切割；最后抛出最牛的利用经纬度进行 RAG 强化。**

### 开场（1 分钟）

> "现在各平台的 AI 要么是个傻傻的通用对话机，要么只能搜死板文案。我在 SmartLive 开发的是带有**强业务转化属性的 AI 中台枢纽站。** 它的核心任务是承接从前端以流数据发射来的 C 端用户，通过无感记忆挂载、司令部下发子路由，联动自身高维向量库最终给出回答 + 落点卡片。"

### C 端记忆拼装流流式输出（3 分钟）

> "针对 AI 对话首要解决的是记忆连贯与打字机响应。如果我靠大表结构硬存容易爆出内存灾难。所有的用户 input 第一时间会被我通过 `ChatMemoryManager` 切片、缓存进短时内存并挂靠在他的线程头上。而在向客户端回显时，我摒弃了传统的 Tomcat 同步等待与大炮打蚊子的 WebSocket，全面切为更契合单向流媒体吐字的轻型 WebFlux + SSE ，确保模型每崩出一个逗号，屏幕都会滑出动感。"

### LlmRoutingAgent 强降维中枢分配（3 分钟）

> "针对问题该回答什么，我不需要去写海量的 Regex 正则表达式判断。这方面，利用我搭建的强型 `LlmRoutingAgent`。用户问：‘这店怎么这么差，什么破服务？’模型总司令部会因为这个语义，自己跳过普通的答疑节点，在代码树中动态走偏门路由唤醒挂在下面的专职 `reviewAgent(差评专家)` 出来擦屁股安抚，这也就是框架级多智能体协同落地的美感。"

### 基于多重过滤的 RAG 幻觉切断（2 分钟）

> "大模型不能闭门造车，需要接地气。所以在处理 O2O 生活需求时。一旦被代理到 `shopAgent`，不仅是通过自然语义去 Milvus 唤醒高度相似性坐标，我还在 API 层将客户端上报的 LBS（经纬度区域）作为强行附加条件并合进入 FilterExpression 发射给底层向量大库。它捞出来的绝不是北京全网相似好吃好玩的，而是牢牢死锁定在消费者三公里圈内，喂进模型重新打包，再吐带上 `card_render` 结构体给手机渲染，做到真真正正的大模型变现！"

### 总结亮点（1 分钟）

> "整个大业务中，这不只是一套包壳聊天 GPT。而是深度融合了：单工极速网络推流 **(SSE)** + 高维意图路由动态中枢 **(Rouing_Agent)** + 原生地理坐标挂靠的私有数据投喂提取 **(Milvus RAG)** 的超维度 O2O 智能交易入口。"

## 5. 高频追问速查表

| 追问方向     | 关键问题                      | 核心回答                                                     |
| :----------- | :---------------------------- | :----------------------------------------------------------- |
| **SSE与WS区别**| 你用 SSE 流式回传，如果发到一半网络断了你怎么恢复续传？ | SSE 本身在 HTTP 1.1 下自带天然断线重连标签（`Last-Event-ID`）。一旦用户拿手机走进没网的隧道，浏览器内核会在恢复后拿着刚刚读到的最后一段索引向我抛异常续接。这是 WebSocket 所不及且需要花大段代码去维护的特性。 |
| **大模型框架** | 阿里的 Spring AI 跟其他 LangChain 之类的库最大优势是什么？| 它与 Java Spring 体系深度吻合对接。可以把我们普通业务的 Service Bean 通过包装上某个注解，极为平滑地注册为供大模型下发思考时随时在云端反回拨调用的 Function Calling（比如拿优惠券接口），而这是 Python 的 Langchain 去联控 Java 业务极难逾越的鸿沟。|
| **卡片解析**   | 在模型一段吐字的文本中间夹杂这 JSON 商铺信息，你代码是怎么做到剔除渲染的？| 我们在 Flux 末尾有一个收口管道 `concatWith`。大模型接收到了极其强硬的 Prompt 指令：必须在完整分析最后，在单独行尾且仅限行尾输出特定 JSON 包格式体。管道会监听最后一段，如果能过审解析类，我将在网络层面直接转换事件标识（EventName）强发特定代码，而不是用发 message 打在文字气泡上。|

## 6. 扩展：这条链路和八股的关联

```
AI多智元引擎生态路由落点 ←→ 八股知识点映射

响应式与高性能网络通信八股：
  ├── Project Reactor 原理初探：Flux 与 Mono 在异步响应管线上的运用
  └── HTTP 原生机制重燃：长连接传输模式 Chunk 运用与 Server-Sent-Events 原理

大模型工业应用新场景：
  ├── Function Calling / Tool Selection（利用参数去动态反调本地接口底层实现）
  ├── RAG（检索增强生成架构）面对私有商业数据大体量向量切块与融合方法论 
  └── LangGraph：使用多结点图机制（Node/Edge）替代死板的链式串行思考与回退
```
